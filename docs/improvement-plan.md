# Grimoire 개선 계획 — 더 빠르게, 더 정확하게, AI가 쓰기 좋게

> 2026-10-25 조사. 2024~2026 코드 로컬라이제이션·에이전트 메모리·MCP 도구 설계 연구와 Grimoire의 현재 코드·벤치 기록을 대조해 정리했다.
> "하지 않는 것"(LLM·임베딩·데몬 없음)은 유지한다 — 조사 결과 이 제약 안에서 올릴 여지가 아직 크다.

## 0. 지금 어디가 막히는가 (벤치 기록 기준)

`bench/results/*confirm*.json`의 grimoire 모드 6문항을 도구 호출 순서로 다시 보면:

| 질문 유형 | 턴 | 호출 순서 | 왜 1턴에 못 끝났나 |
|---|---|---|---|
| 위치 ("어느 파일에 있어?") ×3 | 2 | search → 답 | **이미 1검색으로 끝남** |
| 이력 ("어떻게 풀었지?") ×3 | 3~4 | search → show_commit (×1~2) → 답 | 검색 결과에 **"어떻게"가 없다**. 제목·파일 목록뿐이라 diff를 보러 다시 간다 |

즉 남은 비용의 대부분은 이력 질문에서 나오는 `show_commit` 왕복이다. 개선의 1순위는 "검색 한 번에 '무엇을 어떻게 바꿨는지'까지 실어 보내는 것"이고, 그 재료가 바로 **diff의 식별자**다. 정확도·속도 개선도 이 축을 따라간다.

근거가 된 연구 결과 중 Grimoire의 현재 설계를 **직접 검증**해 주는 것:

- 커밋 이력을 로컬라이제이션 메모리로 쓰면 파일 Acc@1/5가 64.8/71.6 → 68.6/76.5로 오른다. 그 이득의 거의 전부가 **BM25 커밋 검색**에서 나왔고, LLM 요약은 0.2~1.2pt 뿐이었다 (RepoMem, arXiv 2510.01003, 2025).
- 코드 엔티티를 아는 토크나이저(camelCase 분해)의 BM25가 7B 밀집 임베딩을 이겼다 (79.7 vs 73.6 Acc@5, 같은 논문). 식별자 낱말 분해 BM25가 질/지연 면에서 최선이고 BPE는 10~30배 느리면서 이득이 없다 (Practical Code RAG at Scale, NeurIPS 2025).
- 그래프 에이전트(LocAgent, ACL 2025)의 ablation에서 **이름 정확 일치 검색**을 빼면 파일 Acc@5가 88.3→69.0으로 가장 크게 떨어지고, 그래프 탐색을 빼면 86.1로 조금만 떨어진다. 그래프보다 "이름을 정확히 찾는 색인"이 먼저다.

## 1. 더 정확하게

### 1-1. 커밋 diff의 식별자를 색인한다 (효과 최대)

**무엇**: 커밋마다 `git show --format= -p`에서 **추가·삭제된 줄의 식별자**(함수·클래스·변수 이름, 라우트 문자열)와 **hunk 헤더(`@@ … @@ function_name`)** 만 뽑아 `docs_fts`의 새 컬럼(`code`)에 넣는다. 본문 전체가 아니라 식별자 집합이므로 커밋당 수백 바이트다.

**근거**: 커밋 메시지만 BM25로 찾으면 MRR 0.23으로 약하다 (arXiv 2502.07067, 2025). 변경 hunk(바뀐 줄 + 메시지)를 색인하면 MAP가 0.38→0.63 등 6개 프로젝트 모두에서 올랐다 (Locus, ASE 2016). 2024~26 문헌에 "식별자만 추가했을 때" 정확한 수치는 없으므로 1-5의 오프라인 평가로 직접 잰다.

**부수 효과**: `search_memory` 응답에 "이 커밋이 건드린 심볼"을 실을 수 있어 **이력 질문이 1턴에 끝난다**(§3-1).

**비용**: `-p`는 `--numstat`처럼 blob을 diff하므로 느리다. 소스 확장자·200KB 이하 파일만, 커밋당 파일 40개·hunk 줄 2,000줄 상한으로 자르고, 백그라운드 동기화에서 처리한다. 첫 색인은 느려지지만 증분이라 이후는 새 커밋분만이다.

### 1-2. 심볼 엔티티 색인과 정확 일치 가산

**무엇**: 심볼을 "파일 문서의 본문 낱말"로만 두지 말고, `path:Symbol` 정규 이름과 짧은 이름을 별도 테이블(`symbols(repo_id, name, path, line, kind)`)에 두고, 질의 토큰이 심볼 이름과 **정확히**(또는 분해 낱말 전체) 일치하면 재정렬에서 강하게 가산한다. 응답의 `at: ["name:line"]`도 이 테이블에서 꺼낸다(지금은 JSON 문자열을 매번 파싱).

**근거**: LocAgent ablation(위). RepoGraph(ICLR 2025)도 노드는 정의·참조 줄이고, 정의 이름 검색이 시작점이다.

### 1-3. 한국어 음절 바이그램 컬럼 + RRF

**무엇**: 한글 토큰은 JS에서 음절 2-gram("요청횟수제한" → `요청 청횟 횟수 수제 제한`)으로 미리 쪼개 별도 FTS 컬럼(또는 두 번째 FTS 테이블)에 넣고, unicode61 결과와 **Reciprocal Rank Fusion(k=60)** 으로 합친다. 조사 제거(`stripParticle`)와 KO→EN 사전은 질의 쪽에 그대로 둔다.

**근거**: 한국어는 n-gram 색인이 형태소 색인보다 빠르고 효과도 떨어지지 않으며 사전 없이 복합명사를 처리한다 (Lee·Cho·Park, IP&M 1999). 조사 에이전트의 로컬 측정(10만 문서): 바이그램 컬럼은 색인 +11%, 2음절어 질의 25ms. SQLite 내장 trigram은 한글에 3음절 단위라 너무 거칠고(2음절어 질의 불가) 색인이 2.6배 커서 부적합. kiwi·lindera 같은 형태소 분석기는 23~90MB라 "설치 부담 없음" 원칙에 어긋난다.

### 1-4. 사전을 코퍼스에서 자동으로 키운다 (실험적)

**무엇**: 한국어 커밋 제목의 낱말과 그 커밋의 변경 경로·심볼 낱말의 동시 출현(PMI, `fts5vocab`로 집계)을 모아 "충돌→conflict" 같은 쌍을 자동 추가한다. 현재 사전 ~200개의 빈틈(사용자마다 다른 용어)을 메운다. 결정론적이지만 품질은 미측정 — 1-5로 검증 후 채택.

### 1-5. LLM 없는 오프라인 평가 셋 (모든 변경의 전제)

**무엇**: git 이력에서 기계적으로 만든다. 각 커밋에 대해 질의=커밋 제목, 정답=그 커밋이 건드린 파일·심볼, 색인=부모 커밋 시점의 레포(시간 마스킹). 측정은 Acc@1/3/5(파일)·Acc@5(심볼)·MRR. `search()`만 돌리므로 Claude 호출 없이 수초에 끝나고 CI에 넣을 수 있다.

**근거**: LocAgent·SweRank·arXiv 2502.07067의 표준 방법. 제목을 질의로 쓰면 어휘 점수가 부풀므로(알려진 비판), `bench/questions.local.json`처럼 손으로 쓴 자연어 질문 20~50개를 별도 홀드아웃으로 유지한다. 지금의 `npm run bench`(Claude 호출, 회당 $0.3~0.6)는 최종 확인용으로만 남긴다.

### 1-6. 보류: tree-sitter 그래프, 임베딩

- import/호출 그래프 1-hop 확장은 RepoGraph에서 파일 +5.6pt, LocAgent에서 탐색 제거 시 −2~−5.5pt로 이득이 있지만, `web-tree-sitter` + 언어별 WASM(0.2~4.7MB)이 필요하고 함수 단위 질문에서만 크게 유리하다. 1-1·1-2 뒤, 평가 셋에서 함수 Acc@5가 병목으로 확인되면 한다.
- 임베딩: 정적 임베딩(potion-multilingual, <1ms/doc)이 데몬 없이 가능해졌지만 MTEB Retrieval 16점으로 검색엔 약하고 33~130MB 다운로드가 든다. sqlite-vec은 아직 pre-v1. **임베딩 제거 결정을 뒤집을 근거는 없다.**

## 2. 더 빠르게

### 2-1. 커밋 색인: `--name-status`로 읽고 줄 수는 지연 계산

지금 `readCommits`는 `--numstat`로 읽는데, numstat는 blob 내용을 diff하므로 커밋당 ~4ms가 든다(조사 에이전트 로컬 측정: 1,631커밋 6.8s vs `--name-status` 0.13~0.4s, **약 30배**). 추가·삭제 줄 수는 `show_commit` 표시에만 쓰이므로(`overview.ts:197`), 경로·상태만 `--name-status -z`로 색인하고 줄 수는 `show_commit` 때 그 커밋만 계산한다. 10만 커밋 첫 색인이 수 분 → 약 10초.

단, 1-1(diff 식별자)을 하면 `-p` 비용이 다시 붙는다. 그래서 1-1은 **메타 색인과 분리된 2단계**(먼저 메타만 넣어 검색 가능하게 하고, diff 식별자는 뒤에서 채움)로 설계한다.

### 2-2. `git commit-graph write --reachable --changed-paths` 한 번

레포 등록 시 한 번 실행하면 `git log -- path` 류가 2~5배(깊은 트리 10~20배) 빨라진다. 파일별 마지막 커밋(`lastCommit`)을 DB 조인 대신 git에 물을 일이 생겨도 싸다.

### 2-3. 증분 동기화를 `rev-list <tip>..HEAD`로

지금은 매 동기화마다 전체 sha 목록을 받아 DB와 차집합을 낸다(10만 커밋이면 매번 7초 + Set). ref별 마지막 색인 tip을 저장하고 `rev-list --branches --tags --remotes ^<tips>`로 새 sha만 받는다. MCP 프로세스가 살아 있는 동안은 `.git/logs/HEAD`를 `fs.watch`해 커밋·fetch·rebase 직후 갱신한다(데몬 없이 "항상 최신").

### 2-4. 검색 쿼리 수 줄이기

`rerankByCoverage`는 개념마다 FTS `COUNT(*)`와 `MATCH … IN (ids)`를 두 번씩 돌린다(개념 5개면 쿼리 10개). IDF는 `fts5vocab` 테이블(`row` 타입)에서 term당 `doc` 수로 바로 읽고, 매칭 여부는 후보 pool 한 번의 질의에서 `highlight()` 없이 컬럼별 `bm25`로 받는다. 10만 문서에서 공통어 질의 30~60ms가 목표(조사 측정 기준). 1~2글자 접두 질의(`"가"*`)는 금지해 posting list 폭주를 막는다.

## 3. AI가 쓰기 좋게

### 3-1. `search_memory`가 1턴에 답하게: `detail` 단계

**무엇**: `detail: "index" | "summary" | "full"`(기본 `summary`). 
- `index`: 지금 형태(제목·파일 4개·140자).
- `summary`(기본): 커밋 hit에 **본문 전체(상한 600자) + 건드린 심볼(1-1에서 나온 것) + 파일 8개**, 파일 hit에 매칭 심볼과 그 줄 앞뒤 2줄. 상위 1~3개만 이 수준, 나머지는 index.
- `full`: 상위 1개의 diff 발췌(120줄)까지.

**근거**: Anthropic "Writing effective tools for agents"(2025-09)의 `response_format` 패턴(72 vs 206 토큰). claude-mem·GitHub MCP도 `detail`/`fields`로 단계를 나눈다. 벤치에서 이력 질문의 추가 턴은 모두 "어떻게"를 보려는 `show_commit`이었으므로, summary에 심볼·본문이 실리면 **3~4턴 → 2턴**이 기대된다. 응답 예산 e2e(260자/hit)는 `index` 기준으로 유지하고 `summary`는 별도 예산을 둔다.

### 3-2. 모든 응답에 다음 행동 힌트

0건이면 "대체 질의 2~3개(사전 확장·조사 제거 형태)와 `kind`/`repo` 넓히기"를, 잘렸으면 "`show_commit sha=… paths=[…]`"를 `next` 필드로 돌려준다. 여러 sha·여러 질의를 한 호출에 받는다(`queries: []`, `shas: []`) — 벤치 og-css 사례처럼 커밋 두 개를 볼 때 1턴으로 끝난다.

### 3-3. Claude Code 2026 도구 검색에 맞춘 설명·instructions

Claude Code는 기본으로 **도구 이름 + 서버 instructions만** 먼저 싣고 정의는 ToolSearch로 지연 로드한다. instructions와 상시 설명은 4,096자에서 잘리고, 매칭은 앞부분만 본다.
- `instructions`를 **영어로**, 첫 300자에 트리거 문구("where is the code that…", "how did I solve…", "why was X changed", "past commits", "notes")를 넣는다. 한국어는 같은 길이에 토큰이 2배 이상 든다.
- `search_memory`에만 `_meta["anthropic/alwaysLoad"]: true`, 나머지 5개는 지연 로드.
- 읽기 도구 5개에 `annotations.readOnlyHint: true`(병렬 실행·재시도 대상), `add_repo`·`record_note`에 `idempotentHint`. 권한 프롬프트는 안 줄어든다(공개 이슈 #87452).
- 도구 순서를 고정하고 설명을 안정시킨다(프롬프트 캐시 적중).

### 3-4. `grimoire` SKILL.md 동봉

`grimoire install claude-code`가 `~/.claude/skills/grimoire/SKILL.md`도 쓰게 한다. description에 이력·위치 질문 트리거를, `allowed-tools: mcp__grimoire__*`로 호출 턴의 권한 프롬프트를 없앤다. 본문엔 2줄 워크플로("search → 필요할 때만 show_commit")만. Context7·claude-mem이 같은 이유로 스킬을 동봉한다(라우팅 개선 효과는 실무 합의 수준, 미측정).

### 3-5. 노트에 결정론적 메모리 점수

`record_note`에 `commit`/`file` 링크 필드를 두고, 검색 점수에 `− λ·log(1+경과일)` 나이 페널티와 `show_commit`·노트 조회 횟수 가산을 넣는다. 레포 범위 밖 노트는 기본 제외(스코프 게이트).

**근거**: 코딩 에이전트 메모리 연구는 "회수보다 정밀"이다 — 걸러지지 않은 경험 메모리는 이득이 없거나 해롭고(CTIM-Rover 2025, SWE-ContextBench 2026), 규칙 기반 게이트 + 나이 페널티가 효과적이었다(DreamBench-SWE 2026). 모두 LLM 없이 구현 가능.

### 3-6. 하지 않을 것

- `outputSchema`/`structuredContent`: 토큰을 줄인다는 근거 없음, 텍스트도 함께 보내야 함.
- YAML/TOON 등 포맷 교체: 정확도 차이 ≤3pt, 헤더 없는 CSV는 8~16pt 손해. **내용 양**이 레버이지 문법이 아니다.
- elicitation·tasks: Cursor 불안정, headless Claude Code에서 취소됨.

## 4. 순서

| 단계 | 항목 | 효과 | 공수 |
|---|---|---|---|
| 1 | 1-5 오프라인 평가 셋 + CI | 이후 모든 변경을 숫자로 판단 | 1~2일 |
| 2 | 2-1 `--name-status` + 2-3 `rev-list` 증분 + 2-2 commit-graph | 첫 색인 ~30배, 동기화 상수 시간 | 1일 |
| 3 | 1-1 diff 식별자 색인(백그라운드 2단계) + 3-1 `detail: summary` | 이력 질문 3~4턴 → 2턴, 정확도 상승 | 3~4일 |
| 4 | 1-2 심볼 테이블 + 정확 일치 가산 + 2-4 쿼리 수 축소 | 위치 Acc@1 상승, 질의 지연 ↓ | 2일 |
| 5 | 3-3 instructions/annotations/alwaysLoad + 3-2 next 힌트 + 3-4 SKILL.md | 도구 선택·권한 프롬프트·토큰 | 1일 |
| 6 | 1-3 한국어 바이그램 + RRF | 한국어 회수 ↑ (평가 셋으로 확인) | 1~2일 |
| 7 | 3-5 노트 점수·링크, 1-4 자동 사전 | 노트 품질, 사전 빈틈 | 실험 |
| 보류 | tree-sitter 그래프, 정적 임베딩 | 평가 셋에서 함수 단위 병목 확인 후 | — |

각 단계는 `npm run eval`(1-5)의 Acc@k·MRR과 `npm run e2e`의 응답 예산을 통과해야 다음으로 간다. 최종 확인만 `npm run bench`(Claude 호출)로 한다.
