# 레포 규칙 — "규칙의 원본은 규칙 파일, grimoire는 그 규칙이 왜 생겼는지 안다" (2026-10-30)

> 상태: **구현됨 (0.12.0 후보).** "규칙 노트"(#39)를 되돌리고(#41) 이 문서의 방향으로 다시 만들었다.
> 성공 기준은 §5에 만들기 전에 고정했다. 결과와 막다른 길은 §7.

## 0. 한 줄

**규칙은 규칙 파일(CLAUDE.md·.claude/rules·.cursor/rules·AGENTS.md…)에만 있다. grimoire는 규칙을 복제하지 않고, 규칙 한 줄 한 줄이 어느 커밋에서 생기고 바뀌었는지, 그때의 "왜"가 무엇이었는지를 안다.**

요구는 "규칙이 바뀌면 노트도 반드시 바뀐다"였다. 이것을 가장 확실하게 지키는 방법은 규칙을 노트로 복제하지 않는 것이다. 원본이 하나면 어긋날 일이 없다.

## 1. 되돌린 설계(#39)에서 배운 것

| 문제 | 무엇이 잘못됐나 |
|---|---|
| 다른 규칙을 조용히 숨김 | 같은 폴더의 "규칙: 탭 금지"를 "규칙: 세미콜론 금지"가 대신했다. 제목 낱말 자카드 0.67. "규칙"·"금지" 같은 흔한 낱말이 유사도를 끌어올렸다 |
| AI가 사람의 규칙을 내림 | MCP(`by: ai`)가 CLI(`by: me`) 노트를 대신할 수 있었다. 검색 결과가 둘을 나눠 보여 주는 이유를 거스른다 |
| 폴더 규칙의 신선도 없음 | 폴더에는 blob이 없어 stale을 못 쟀다 |
| 기존 도구와 겹침 | Claude Code `.claude/rules`(`paths`)·Cursor globs·Copilot `applyTo`·Kiro `fileMatch`가 이미 "이 경로를 건드릴 때만 이 규칙"을 한다. signal-design 원칙 6 위반 |
| 잴 수단 없이 만듦 | 원칙 5(만들기 전에 잴 수단부터)를 건너뛰었다 |

## 2. 비슷한 도구 조사

두 부류가 있다.

**사람이 쓰는 규칙 파일** — 경로 패턴으로 범위를 정하고, 바꾸는 것은 파일 수정, 이력은 git.

| 도구 | 위치 | 범위 |
|---|---|---|
| Claude Code | `CLAUDE.md`(하위 폴더도), `.claude/rules/*.md` | `paths` 프런트매터, 하위 폴더 CLAUDE.md는 그 폴더 |
| Cursor | `.cursor/rules/*.mdc`, 옛 `.cursorrules` | `globs`, `alwaysApply` |
| Copilot | `.github/copilot-instructions.md`, `.github/instructions/*.instructions.md` | `applyTo` |
| Windsurf | `.windsurf/rules/`, 옛 `.windsurfrules` | 트리거 설정 |
| Kiro | `.kiro/steering/*.md` | `fileMatchPattern` |
| 공통 | `AGENTS.md` | 늘 |

**에이전트가 쓰는 기억** — 어긋남과 오래됨을 스스로 다뤄야 하고, 거기서 갈린다.

- **mem0**: 비슷한 기억을 찾아 LLM이 ADD/UPDATE/DELETE/NOOP을 고른다. 상황별 선호를 조용히 지운 사례가 보고됐다 — #39의 버그와 같은 종류.
- **Zep/Graphiti**: 모순되는 사실은 지우지 않고 `invalid_at`을 찍는다. 판정은 LLM이 "명시적 모순일 때만". 이것도 LLM 판단에 맡긴다는 비판(공존 불가 술어를 선언하자는 반론)이 있다.
- **Copilot Memory**: 기억마다 코드 위치를 근거로 붙이고, 쓰기 직전에 그 근거가 지금도 맞는지 확인한다. 안 맞으면 고쳐 저장, 28일 지나면 만료.
- **Windsurf**: 오래 갈 지식은 자동 기억이 아니라 Rules나 AGENTS.md에 두라고 문서가 권한다.
- **ADR(adr-tools·log4brains)**: 옛 결정에 "Superseded by ADR-N"을 달고 양방향 링크. 지우지 않는다.
- **보안**: OWASP 에이전트 Top 10 2026의 ASI06 "메모리·맥락 오염". "항상 X를 하라" 꼴의 기억은 사람이 검토하고, 정책은 기억 층이 아니라 AGENTS.md에 두라는 권고가 공통이다.

## 3. 결론

1. **규칙의 원본은 규칙 파일이다.** grimoire는 규칙을 쓰지도, 고치지도, 숨기지도 않는다. 그래서 자동 교체·AI 권한·유사도 판정 문제가 생기지 않는다.
2. **규칙 텍스트를 훅으로 다시 주입하지 않는다.** 클라이언트가 이미 싣는다(원칙 6).
3. **grimoire가 더하는 것은 이력과 왜다.** 규칙 단위마다 그 줄을 들여온 커밋(출처)과 마지막으로 바꾼 커밋, 그 커밋에 묶인 왜(캡처된 프롬프트·트레일러). git blame으로 구하고, 규칙 파일의 blob이 바뀐 동기화에서만 다시 구한다.
4. **규칙이 바뀌는 순간에 출처를 보여 준다.** 규칙 파일을 고치기 직전(PreToolUse), 지금 고치거나 지우는 규칙이 어느 커밋에서 왜 들어왔는지 한 줄씩. 결정이 일어나는 순간이고(원칙 4), 코드로 복원할 수 없는 정보다(원칙 1). 고치는 규칙에 출처·왜가 없으면 아무 말도 하지 않는다(원칙 2).
5. **규칙 파일에 묶인 노트는 규칙 파일이 바뀌면 stale이 된다.** 지금은 소스 파일(code_files)만 blob을 알아 CLAUDE.md에 묶은 노트는 영원히 "최신"이었다. 규칙 파일의 blob도 알게 해서 "규칙이 바뀌면 그 규칙에 대한 노트는 오래됐다고 표시된다"를 기계적으로 지킨다.

## 4. 설계

### 4-1. 찾는 파일 (HEAD 트리, 200KB 이하)

`CLAUDE.md`·`AGENTS.md`(어느 폴더든), `.claude/rules/**/*.md`, `.cursor/rules/**/*.{mdc,md}`, `.cursorrules`, `.windsurfrules`, `.windsurf/rules/**/*.md`, `.github/copilot-instructions.md`, `.github/instructions/**/*.instructions.md`, `.kiro/steering/**/*.md`. 레포 하나에 50개까지.

### 4-2. 규칙 단위

마크다운을 단위로 나눈다. 목록 항목 하나(이어지는 들여쓴 줄 포함)가 단위 하나, 목록이 아닌 문단 하나가 단위 하나. 제목은 단위가 아니라 그 아래 단위의 맥락(`heading`)이다. 코드 블록은 앞 단위에 붙인다. 프런트매터는 빼되 범위(`paths`·`globs`·`applyTo`·`fileMatchPattern`)는 문자열로 남겨 보여 준다. 글자 수 8 미만인 단위는 버린다.

### 4-3. 이력

`git blame --porcelain -w -M HEAD -- <file>`로 줄마다 "지금 글자를 쓴 커밋"을 얻는다. 단위의 **출처**는 그 줄들 중 가장 이른 커밋, **최근 변경**은 가장 늦은 커밋(순서는 committer-time — author-time은 rebase·cherry-pick 뒤 옛 날짜로 남는다). 공백만 바꾼 커밋은 `-w`로 건너뛰고, 파일 안에서 옮긴 줄은 `-M`으로 옮기기 전 커밋을 본다. 더 거슬러 가지 않는다(§7 막다른 길 1). 커밋의 왜는 저장하지 않고 보여 줄 때 구한다 — 캡처는 커밋 뒤에 붙기도 하므로.

### 4-4. 저장과 검색

- `rule_files(repo_id, path, blob)` — 바뀐 파일만 다시 blame.
- `rules(repo_id, path, line, end_line, heading, scope, text, origin_sha, last_sha)`.
- 검색 문서 `kind='rule'`, `ref='path:line'`. `search_memory`의 `kind`에 `rule`을 더한다. 결과: 규칙 위치, 본문 발췌, 출처 커밋(sha·날짜·제목·왜), 최근 변경이 다르면 그것도.
- 새 MCP 도구는 만들지 않는다(도구 정의 예산).

### 4-5. 훅

규칙 파일을 `Edit`/`MultiEdit`로 고치기 직전: `old_string`을 지금 파일에서 찾아 그 줄 범위와 겹치는 규칙 단위(줄 번호도 지금 파일 기준). `Write`로 통째로 쓰기 직전: 새 내용에 같은 글자의 단위가 없는 규칙 단위. 그중 출처 커밋 제목이 이유를 담을 만한 것(`isRuleWorthCommit` — 병합·오타·형식·릴리스·버전 올림·"Update CLAUDE.md"가 아님)만, 최대 3개, 400자. 왜가 있으면 붙인다 — 캡처를 안 쓰는 레포에서도 커밋 제목이 대개 이유를 담는다. 그리고 이 파일에 묶인 노트. 세션·파일·HEAD당 한 번.

### 4-6. 하지 않는 것

규칙 텍스트 주입, 경로 범위 매칭, 규칙 강제(린트·테스트의 몫), 규칙 쓰기·숨기기, LLM 판정.

## 6. 정체성과의 관계

signal-design §0은 "grimoire는 커밋 뒤의 왜를 저장하고 꺼내 주는 기억"이다. 규칙 파일은 팀의 결정이 가장 압축된 곳이고, "이 규칙 왜 있지"는 그 결정의 왜를 묻는 질문이다. §5-2에서 보류한 "지뢰 경고"(바꾸려는 줄의 출처 커밋과 왜)를 규칙 파일에만 먼저 적용하는 셈이기도 하다 — 규칙 파일은 작고 드물게 바뀌어 blame을 미리 해 둘 수 있고, 규칙을 바꾸는 순간은 결정의 순간이다.

### 7-2. 실제 레포 (anthropics/claude-code-action, 827커밋, 규칙 파일 2개·49단위)

출처가 실제 이력과 맞는다: CLAUDE.md를 통째로 고쳐 쓴 9a3c761(117줄 → 25줄), 보안 절을 들인 a8cb0db, 그 뒤 고친 7057f33. 훅은 MultiEdit 두 곳에 두 줄(326자), 제목만 고친 편집에는 아무것도. 훅 전체 실행(node 기동 포함) 75ms.

### 7-3. 막다른 길 — 구현 중에 실제 데이터와 반례가 잡은 것

1. **`git log -L`로 "처음 들인 커밋"까지 거슬러 가기.** blame은 줄의 "지금 글자를 쓴 커밋"만 안다. 그래서 한 줄짜리 규칙을 고쳐 쓰면 처음 들인 커밋을 잃는다. `git log -L`로 범위를 따라가면 되찾을 것 같았지만, 실제 레포에서 파일을 통째로 고쳐 쓴 커밋을 지나 첫 커밋까지 가서 규칙 대부분의 출처가 "Initial commit"이 됐다. 줄 범위는 내용과 상관없이 이어지기 때문이다. git이 증명하는 것은 "이 글자를 쓴 커밋"까지다 — 버렸다. 되찾는 것은 다시 유사도 판정이 되고, 그것이 #39를 망친 방식이다.
2. **날짜로 "가장 이른" 커밋 고르기.** author 날짜는 rebase·cherry-pick 뒤 부모보다 이를 수 있다. 반례 테스트에서 나중 커밋이 출처로 뽑혔다 → blame은 committer-time으로 본다.
3. **meaningful.ts로 훅 출처 거르기.** 그 판정은 `docs:`·`ci:`·`chore:`를 모두 뺀다. 규칙 파일을 바꾸는 커밋은 대개 그 접두라, 실제 레포에서 보안 규칙 전부가 훅에서 빠졌다 → 이유 없는 제목만 빼는 `isRuleWorthCommit`.
4. **목록 기호로 시작해 줄 중간에서 끝나는 편집을 놓침.** 규칙 단위는 첫 줄의 목록 기호를 떼고 저장하는데, 편집 내용은 기호를 단 채 비교했다. 실제 레포의 MultiEdit에서 한 곳을 놓쳤다 → 양쪽 다 줄마다 기호를 떼고 비교.

### 7-4. 독립 리뷰가 잡은 것 (구현과 결론을 모르는 리뷰어, 재현 후 수정)

| 잡힌 것 | 고친 것 |
|---|---|
| 두 줄짜리 규칙에서 커밋 시각이 같으면(rebase·`git am`) 출처가 거꾸로 | 파일 이력 순서(`git rev-list --topo-order`)로 고른다. 순서를 모를 때만 시각 |
| 심볼릭 링크 `AGENTS.md -> CLAUDE.md`가 "CLAUDE.md"라는 규칙으로 들어감 | mode 120000은 뺀다 |
| 400자에 잘린 규칙도 "보였다"로 적혀 그 세션 내내 안 나옴, 규칙이 다 잘리면 빈 머리말 | 실제로 나간 규칙만 적는다. 노트 줄은 남기고 규칙부터 뺀다 |
| 글자 비교 매칭: 표 구분선 `\|---\|---\|` 같은 흔한 줄이 다른 규칙에 걸림, 8자 미만 편집은 못 잡음, 앞에 덧붙여 바꾼 규칙을 Write에서 못 잡음 | 짐작을 버리고 위치로: old_string을 지금 파일에서 찾아 그 줄 범위와 겹치는 단위. Write는 단위 글자 집합 비교 |
| 커밋 안 한 편집이 앞에 줄을 더하면 HEAD 줄 번호를 댐 | 지금 파일을 읽어 지금 줄 번호. 출처는 같은 글자의 색인된 규칙에서 |
| 빈 줄 뒤 코드 블록이 앞 단위에 안 붙음, 네 개짜리 울타리가 세 개에 닫힘, 밑줄 꼴 제목이 규칙이 됨 | 파서 수정 |
| blame 실패가 그 파일의 출처를 영영 비워 둠 | `rule_files.complete = 0` → 다음 동기화가 다시 읽는다 |

### 7-5. 남은 한계

- 규칙을 고쳐 쓰면 출처는 고쳐 쓴 커밋이 된다(§7-3-1).
- 규칙 파일 50개·200KB 상한 밖의 파일, 이번 변경 전에 남긴 노트는 blob을 몰라 stale을 재지 않는다. 그 커밋의 왜가 "왜 지금 이렇게 쓰여 있나"에 대한 답이다.
- 경로 범위(`paths`·`globs`)는 보여 주기만 하고 맞추지 않는다. 클라이언트가 한다.
- 규칙이 지켜지는지는 보지 않는다. 기계로 잴 수 있는 규칙은 린트·테스트로 옮기는 것이 맞다.
