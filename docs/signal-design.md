# 다음 설계 — "커밋 뒤의 '왜'를 저장하고, 물으면 꺼내 준다" (2026-10-27)

> 상태: **방향 확정 (2026-10-27), 구현 전.** 결정은 §4, 단계는 §8에 있다.
> 근거: taskbench 측정 (grimoire 노트 #22, #23), 설계 결정 (노트 #24), docs/enhancement-plan.md §3·§9.
> 이 문서는 같은 날 작성한 초안("코드가 말해 주지 않는 것만, 필요한 순간에")을 대체한다. 초안의 신호 설계는 부록 A에 보류 상태로 남겼다.

## 0. 정체성

**grimoire는 커밋 뒤에 있던 사람의 의도와 결정을 저장하고, 사람이든 에이전트든 "왜"를 물으면 바로 꺼내 주는 레포 기억이다. 에이전트의 자율 수정 성능은 목표가 아니다.**

- git은 "무엇이 바뀌었나"를 안다. grimoire는 "왜 그렇게 했나"를 안다. 캡처된 프롬프트·노트가 커밋에 묶여 있다는 점이 다른 도구에 없는 자산이다.
- 가치는 재료가 쌓일수록 복리로 는다. 그래서 투자는 **캡처의 품질**(왜가 커밋에 얼마나 잘 붙나)과 **검색의 품질**(물었을 때 몇 턴 안에 맞는 답이 나오나)에 둔다.
- 훅은 맥락을 쏟는 층이 아니라, "왜"를 물어야 할 순간에 기억이 있다는 걸 떠올리게 하는 얇은 층이다.

## 2. 진단

1. **지금 훅은 "파일 카드"다.** 최근 커밋, 공변경, 테스트처럼 모델이 `git log`나 import를 읽으면 스스로 알 수 있는 정보를 건넨다. 좋은 모델은 그 정보 없이도 대부분 푼다.
2. **편집 직전 카드는 에이전트가 이미 계획을 세운 뒤에 도착한다.**
3. **측정 과제는 프롬프트에 해법까지 적혀 있어서, 기억 없이도 풀렸다.**
4. **목표와 측정이 어긋났다.** 세션 목표는 "개발자와의 협업 효율화"인데, 측정은 "에이전트 혼자 고치는 비용"을 봤다. 어긋난 측정으로 어긋난 결론을 내리는 중이었다.
5. **에이전트가 기억을 당겨 쓰지 않는 것(0/20)은 기능의 문제가 아니라 지시의 문제다.** CLAUDE.md의 "이력 질문이면 `search_memory` 먼저" 규칙이 그 자리를 맡는다.

유일하게 확인된 가치는 "예전에 뭘 했지 / 왜 이렇게 됐지"를 빨리 찾아 주는 것이다. 이것은 코드에 없는 정보, 즉 사람의 의도와 결정이다. §0은 여기서 나왔다.

## 3. 원칙

1. **코드에서 복원할 수 없는 것만 말한다.** 실패·되돌림, 버린 대안, 제약, 사람의 의도, 검증 기록. 최근 커밋 목록은 들지 않는다.
2. **기본값은 침묵이다.** 짧고 틀린 맥락은 없는 것보다 해롭다 (SWE-ContextBench: 틀린 요약 −4pt).
3. **파일보다 지금 건드리는 줄에 묶는다.**
4. **결정이 일어나는 순간에 준다** (바꿀 때 / 끝낼 때 / 막혔을 때).
5. **효과는 미리 고정한 기준으로 잰다.** 만들기 전에 잴 수단부터 둔다.
6. **기존 도구와 겹치는 것은 만들지 않는다.** CLAUDE.md, Claude Code 메모리·압축 요약·작업 목록이 하는 일은 grimoire가 하지 않는다.

## 4. 확정한 결정

1. **정체성은 §0이다.** 에이전트 자율 수정 신호(지뢰 경고·빠진 짝·되돌림 고리)는 보류한다. 재개 조건은 §8에 있다.
2. **Read 훅은 추가하지 않는다.** (Read는 아주 자주 불려 매번 node 기동 비용 50~80ms가 붙는다.)
3. **줄 출처가 필요해지면 훅에서 `git blame -L`로 구한다.** 120ms를 넘으면 건너뛰고, 세션 안에서는 결과를 다시 쓴다. 색인 때 미리 저장하지 않는다. — 보류한 신호와 함께 묶인 결정이라 당장 구현하지 않는다.
4. **SessionStart "최근 커밋 요약"은 기본으로 끈다.** 설정으로만 켠다.
   - 그 자리를 "남은 일·지켜야 할 규칙"에 쓸지는 §6-1 확인 뒤에 정한다. 겹치는 도구가 있으므로 기본은 "안 쓴다".
5. **이번 범위는 Claude Code 훅과 MCP 도구다.** 신호·검색 계산은 `src/core`에 둬서 나중에 Codex·Cursor로 꺼낼 수 있게 한다.
6. **패키지(`dist`)가 안 바뀌는 변경만으로는 배포하지 않는다.**

## 6. 만들기 전에 할 공짜 확인 (C0) — 결과 (2026-10-27)

모두 읽기만 했다. 실제 DB(`~/.grimoire`, 스키마 9)는 `node:sqlite` readOnly로 열었고, git은 read-only 명령만 썼다.

1. **CLAUDE.md에 상시 규칙을 적고 며칠 써 본다.** → 아직 못 함(며칠이 필요하다). 다만 2번에서 같은 규칙의 반복이 이미 잡혔다: "머지·배포는 내가 말할 때" 7회(87개 중), "한국어로 답해" 2회. 사용자 CLAUDE.md에 이 두 줄을 적는 것이 다음 할 일이다. 적은 뒤에도 반복되면 §5-3을 재검토한다.
2. **캡처된 프롬프트 87개(중복 제거) 분류.** 작업 요청 52(60%), 결정·피드백 20(23%), 상태 질문 6(7%), 노이즈 4, **"왜" 질문 3(3%), 반복 규칙만 말한 것 2.** 중앙값 31자, 61%가 40자 미만. "왜" 질문 3건은 모두 "이 세션에서 뭘 바꿨나"였고, **과거 커밋의 "왜 이렇게 했지"형은 0건**이었다.
   → 읽는 법: 이 하루치 캡처는 모두 grimoire 자체 개발 세션이라 사용자가 이력을 묻는 대신 설계를 지시했다. "왜" 질문이 0이라고 검색 가치가 없다는 뜻은 아니지만, **협업 지표 중 지금 당장 잴 수 있는 것은 반복 지시와 상태 질문**이다. 상태 질문 6건("고쳤냐?", "왜 하다 멈춤")은 Claude Code의 작업 목록이 맡는 영역이라 §5-3 판단(접음)을 유지한다.
3. **재발 쌍.** grimoire 4쌍(fix 11개, revert 0), TerraLink 151쌍(보수적 정의로도 121쌍; fix 커밋 97개 = 47%, revert 0). 임계치 30은 TerraLink에서 충족.
   → 다만 TerraLink의 상위 F 셋은 55~107개 파일을 바꾼 대규모 리팩터에 fix 라벨이 붙은 커밋이다("코드 구조 개편", "NUnit 도입"). "버그 수정 줄이 다시 고쳐짐"보다 "fix로 표시된 리팩터 줄이 다시 고쳐짐"이 상당 부분이다. 측정은 가능하지만 지뢰 경고가 그 레포에서 자주 뜨면 대부분 리팩터 줄을 가리킬 것이다. **재개 조건 둘 중 "측정 가능"은 채워졌고 "왜 재료 충분"은 아니다** → S0 보류 유지.
4. **캡처 커버리지.** 커밋에 프롬프트가 묶인 sha는 전체 9개. meaningful 커밋 기준 grimoire 2.6%, 전 레포 0.1%. 그러나 원인을 보면:
   - 0.8.0 전 훅은 워크트리에서 만든 커밋을 세션 폴더(main)의 HEAD에 묶었다. 한 세션의 기록 54건이 **릴리스 커밋 두 개**(06c27b84, 00b13eb9)에 쌓였고, 그 커밋의 "왜"가 됐다. 0.8.0(05:14Z)부터는 묶임이 전부 정확하다.
   - 0.8.0 이후 세션에서 만든 커밋 6개 중 5개가 묶였다(나머지 1개는 설치 직전). squash 커밋은 change_key로 브랜치 커밋의 왜를 받는다. **지금 캡처는 새는 곳이 없다.** 낮은 숫자는 캡처가 10-26에 시작됐기 때문이다.
   - 서브에이전트(agent_id)가 한 편집·검증·커밋은 전부 건너뛰고 있었다 — 위임한 작업의 커밋에는 왜가 붙지 않는 구조적 누수.
   → 할 일: 오염 기록 정리(마이그레이션), 서브에이전트 커밋 묶기, 그리고 "고쳤냐?" 같은 상태 질문이 "왜"로 뽑히지 않게.
5. **노트 25개.** 전부 grimoire 레포, 14개가 파일 경로를 본문에 적었다. 태그: decision 8, lesson 3, benchmark 3. → 노트를 파일에 묶는 재료는 이미 있다.

## 7. 효과 측정 계획

### 7-1. 협업 지표 (정체성에 맞는 지표, 우선)

캡처된 프롬프트로 전후를 비교한다. 결과를 보기 전에 기준을 고정한다.

| 지표 | 뜻 | 기준 |
|---|---|---|
| "왜" 질문의 해결 턴 수 | 사람이 왜를 물은 뒤 맞는 커밋·노트가 나오기까지의 에이전트 턴 | 중앙값 1턴, `search_memory` 첫 호출에서 적중 |
| 캡처 커버리지 | 커밋 중 왜(프롬프트·노트)가 묶인 비율 | §6-4의 현재값 대비 상승 |
| 같은 지시 반복 횟수 | 세션당 | §6-1·6-2 뒤 판단 |
| 상태 질문 수 | 세션당 | §6-2 뒤 판단 |

### 7-2. 자율 수정 지표 (보류한 신호를 꺼낼 때만)

- **재발 과제:** fix 커밋 F 뒤에 같은 줄을 다시 고친 커밋 G. G 직전 시점에서 과제를 주고, G와 F의 테스트가 모두 통과하는지 본다. 채택 기준: 재발률이 15pt 이상 낮을 것, 사례 30개 이상, 맥니마 p < 0.05.
- **여러 파일 과제:** 비테스트 파일 2~5개를 고친 fix 커밋. 채택 기준: `missed`가 0.1 이상 줄 것.
- **공통:** 주입 정밀도가 0.5 미만인 신호는 끈다.

## 부록 A. 보류한 신호 설계 (초안에서 옮김)

§8의 S0~S3을 꺼낼 때 그대로 쓰기 위해 남긴다. 결정 §4-2·4-3이 여기에 묶여 있다.

### A-1. 세 순간과 그때 줄 것

| 순간 | 훅 | 줄 것 |
|---|---|---|
| **바꿈** — 편집 직전 | PreToolUse `Edit·Write` | **지뢰 경고**: 지우거나 바꾸는 줄(`old_string`)이 fix 커밋으로 들어왔거나, 되돌림·재수정 이력이 있거나, 제약 노트가 묶여 있으면 그 커밋과 그때의 왜 |
| **끝냄** — 검증 통과 직후 | PostToolUse `Bash` | **빠진 짝**: 이번 세션에 고친 파일들과 늘 같이 바뀌던 파일·테스트 중 아직 안 건드린 것 |
| **막힘** — 첫 검증 실패 | PostToolUse `Bash` | 고치는 파일들의 왜, 검증, 버린 편집, rejected·constraint (지금과 같다) |

### A-2. 지뢰 경고 (바꿈)

- 입력: `old_string`의 줄들. Write라면 덮어쓰는 파일에서 사라지는 줄들이다.
- 재료: 그 줄들의 출처 커밋. 출처 커밋이 fix 커밋(FIX_SUBJECT)이거나, 나중에 되돌림이나 재수정이 있었거나, 커밋에 `rejected`·`constraint` 트레일러나 캡처된 의도가 있으면 신호가 된다.
- 출력 예:
  `Grimoire: lines you're replacing came from 3fd5172 "fix(ts-recalc): 같은 기계점의 모든 행에 적용" — why: "후방교회 세션 한 행만 바뀌던 문제" · verified: vitest ts-recalc`
- 조용할 때: 출처가 평범한 기능 커밋이고 붙은 의도도 없으면 아무것도 내보내지 않는다.

### A-3. 빠진 짝 (끝냄)

- 이 세션에서 고친 파일 집합 E를 놓고, E와 강하게 공변경되는 파일(confidence ≥ 0.6, support ≥ 3)과 짝 테스트를 본다. 그중 E에 없는 것만 남긴다.
- 검증이 통과한 직후 **한 번만** 준다.
- 출력 예: `Grimoire: files that changed together with what you edited, not touched yet: backend/src/ts/recalc.repo.ts (7/9)`

### A-4. 되돌림·재수정 고리 (지뢰 경고에 합침)

- 색인할 때 커밋 쌍을 찾아 둔다. (a) `Revert "…"`나 `This reverts commit <sha>`, (b) 30일 안에 같은 줄 범위를 다시 고친 fix 커밋.
- 바꾸는 줄의 출처 커밋이 고리에 속하면 지뢰 경고에 한 줄을 더한다: `tried in a1b2c3, reverted by d4e5f6 — <되돌린 이유>`

### A-5. 새로 필요한 재료

| 재료 | 만드는 법 | 비용 |
|---|---|---|
| 줄 출처 | 훅에서 `git blame -L` (해당 줄 범위만, `--porcelain`). 120ms를 넘으면 끊고 조용히 건너뛴다. 같은 세션·파일·HEAD의 결과는 세션 상태에 캐시한다 | 파일·범위에 따라 20~200ms. 큰 파일에서는 가끔 경고를 놓친다 |
| 되돌림·재수정 고리 | 색인 시 커밋 메시지(revert)와 diff 줄 범위 겹침으로 계산해 `fix_chains` 테이블에 저장 | 색인 시간이 조금 는다 |
| 파일에 묶인 노트 | `record_note`에 `paths`를 받거나, 노트 본문의 경로를 뽑아 연결 — **§5-1 K3에서 먼저 만든다** | 스키마 한 칸 |
| 세션 편집 집합 | 이미 있다 (`session_events`의 edit) | 없음 |

### A-6. 재개 조건 요약

- C0-3에서 재발 쌍이 두 레포 합쳐 30개 이상일 것 (측정 가능성).
- K1~K4가 끝나 "왜" 재료가 커밋에 충분히 붙어 있을 것 (지뢰 경고가 보여 줄 "왜"가 있어야 한다).
- 둘이 채워지면 S0부터 §7-2 기준으로 진행한다.
